# Resource tracking and 12-week applied study plan
## Minimal resource record (private or sanitized)
Resource | URL | Topic | publisher/source | last checked YYYY-MM-DD | access status | why it matters now | 1 practical exercise | linked issue | evidence generated | next review date.
Only mark **applied** when work changed or was tested; “read” is not “validated”.

## Suggested first 12 weeks (adjust to shift work)
| Week | Learn | Applied FieldLab task |
|---|---|---|
| 1 | YC talking to users, The Mom Test | 3 actual interviews, remove leading questions |
| 2 | BPO/QA workflows and existing alternatives | 4 more interviews, document current substitute |
| 3 | Startup ideas + do things that don't scale | Offer one manual procedure test |
| 4 | Company problem statement and evidence standards | Review 15+ interview attempts, decide what remains unknown |
| 5 | Product scope / usability basics | Sketch 4-screen minimal product, user test paper prototype |
| 6 | Python, SQL, REST | Implement one immutable version record locally |
| 7 | Typed schemas, validation, testing | Build controlled rule/decision data contract |
| 8 | Deterministic regression testing | Implement boundary/missing-data/abstention tests |
| 9 | Gemma 4, local runtimes | Reproduce offline local-model E4B exploration on fictional cases |
| 10 | Experimental design and LLM security | Compare human/spreadsheet/Gemma with source validation |
| 11 | Pricing, pilot offer and unit economics | Calculate actual labor cost, ask buyer for bounded paid test |
| 12 | Founder sales, finance and startup updates | Write a go/narrow/pivot decision and next 12-week plan |
**Warning:** these are learning examples. Stage 0 customer discovery can and should delay expensive coding if real pain remains unproven.

## Daily/weekly learning protocol
- 30–60 min, 2–4 sessions per week as feasible; explain the concept from first principles.
- Minimum one real customer action each week while in discovery.
- Record one test/decision and the error it exposed.
- Review source quality: official doc? vendor marketing? replicated independent findings? anecdote?
- Evaluate updates quarterly; avoid stale tool-specific instructions and paid courses not aligned with current work.

## Skill progression (technical)
Operating system & network → Python and local process → HTTP/browser → validation and databases → CI/testing → storage and auth → data security → LLM runtimes and model evaluation → hosted infrastructure if customers require it. For each, debug one failure manually.

## Skill progression (business)
Actual problem observation → customer interviews → positioning vs alternatives → manual solution → prototype → distribution/selling → paid pilot → repeat use → accurate unit economics → organization/legal/fundraising decisions. Every transition has evidence criteria.

## Recommended operating file structure
- GitHub (public): code, fictional fixtures, source citations, sanitized learning, issues and decision principles.
- Secure private notes: named customer interviews, contacts, permitted policy samples, contracts, risk review, actual financial transactions.
- YC Startup School account: weekly progress reports consistent with measured facts; not a replacement for issue-level evidence.
- Quarterly resource audit: re-check 10 most actionable links and replace stale courses; do not spend a week cataloging links instead of meeting buyers.

## Quarterly research question prompts
What changed in local models, licenses, security? Which customer pain has become more/less urgent? Which vendor now solves our wedge? Did a model upgrade change false-positive rates? What did customers pay and repeat? What legal/immigration assumptions need new advice? What course did I apply, not just consume?
